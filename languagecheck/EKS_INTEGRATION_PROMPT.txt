TASK
Integrate the "non-English feedback flagger" into our service and deploy it on
Amazon EKS. Read README.md first, then flag_non_english.py. Do not rewrite the
detection logic; wrap and deploy it.

WHAT THE MODULE DOES
- check_feedback(text) -> Result. Result.to_dict() is JSON-serializable.
- Flags a comment if ANY part is not English (including mixed English+Spanish).
  English is the only allowed language.
- Result fields: flagged (bool, the decision), languages, reasons
  (SCRIPT|SEGMENT|TOKEN|ERROR), reason_descriptions, evidence, error.
- It never raises. On an unexpected error it returns flagged=True with
  reasons=["ERROR"] so a person reviews the comment.
- All thresholds are in the Config dataclass (see README "Settings").

DEPENDENCIES - KEEP PINNED
- requirements.txt pins: lingua-language-detector==2.2.0 and wordfreq==3.1.1.
  Install exactly these. Do NOT unpin, loosen, or upgrade them: a library update
  can change which comments are flagged.
- pytest==9.2.0 is dev-only (requirements-dev.txt). Do not install it in the
  runtime image.
- Tested on Python 3.14. Use the same Python version in the Docker image, or
  run the full test suite inside the built image and confirm it passes before
  using a different version.
- Both libraries ship their own data. No downloads, API keys, or network access
  are needed at runtime. The image must work with no outbound internet.

STARTUP LOADING - REQUIRED
- The language models load once per process, lazily on the first
  check_feedback() call (a few hundred MB, ~0.5 s locally). Without a warm-up
  the first request is slow.
- Call flag_non_english.warmup() during application startup, BEFORE the pod can
  report Ready. Use FastAPI's lifespan (or equivalent startup hook).
- /health (liveness): returns 200 as soon as the process is up. Do not call the
  detector in it.
- /ready (readiness): returns 200 only after warmup() has finished; 503 before.
  Also use a startupProbe with a generous failureThreshold so a slow node does
  not get the pod killed while models load.
- Never create a new process per request. Load the models once per process.
- If you run multiple workers (gunicorn/uvicorn), each worker holds its own
  copy of the models. Either call warmup() before forking and use --preload so
  memory is shared, or run ONE worker per pod and scale with pods. Prefer one
  worker per pod.

API TO BUILD (FastAPI)
- POST /check        body {"text": "..."} -> returns Result.to_dict().
- POST /check/batch  body {"texts": ["...", ...]} -> list of Result.to_dict(),
  same order as input. Accept up to ~5,000 items (testing sends 5,000 at once).
  The work is CPU-bound (~390 comments/second on one CPU): run it in a
  threadpool or as a background job so the event loop and probes are not
  blocked. If a batch can exceed the HTTP/ingress timeout, accept it and return
  a job id, or stream results. Pick one and document it.
- Validate input: text must be a string; enforce a max length (Config.max_chars
  already truncates, but also reject bodies above a sane size).
- Production traffic: ~100 comments/day, plus bursts of ~5,000 during testing at
  irregular times.
